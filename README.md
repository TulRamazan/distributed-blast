# Distributed BLAST: Breaking the Bottleneck

Project 25, Track E (Alignment, Search and Scale) -- Introduction to
Bioinformatics, Course Project. A distributed search system with a
documented scaling analysis and an honest comparison against modern
alternatives (DIAMOND, MMseqs2).

## What this is

The institute's shared BLAST server has an hours-long queue. This project
asks: where and why does a single-node BLAST search actually break down
as databases and query sets grow, and does splitting the work across
workers actually fix it? We build and measure two distributed-search
strategies (query partitioning and database partitioning) on real
reference databases and real NGS/TGS-derived query workloads, and compare
against DIAMOND and MMseqs2.

See `report/` for the full 8-12 page report (problem framing, methods,
results, and a Limitations section -- read that section closely, several
constraints of the development environment are disclosed there and
matter for interpreting the results).

## Setup (from a clean machine)

1. Clone this repository.
2. Install the pinned toolchain -- either:
   - `mamba env create -f environment.yml && conda activate distributed-blast`, or
   - `docker build -t distributed-blast .` (see Dockerfile)
3. Check versions match what this project was benchmarked against:
   `blastx -version`, `diamond version`, `mmseqs version` should report
   2.12.0, 2.1.x, 15.x respectively (see `environment.yml` for exact pins).
4. Run the small verification test (no data download needed, <1 minute):
   `bash test/run_smoke_test.sh`
5. Fetch the real data (see "Data sources and the network limitation"
   below -- this step behaves differently on an unrestricted network):
   `bash scripts/fetch_data.sh`
6. Build the reference databases (Task 2):
   `python3 scripts/build_databases.py`
7. Build the query workloads (Tasks 4/5):
   `python3 scripts/build_workloads.py`
8. Reproduce the headline result -- the measured scaling curve (Tasks 6/7):
   `python3 scripts/scaling_benchmark.py`
9. (Optional, a few more minutes) Run the tool comparison (Task 8) and the
   database-growth model (Task 3):
   `python3 scripts/tool_comparison.py && python3 scripts/db_growth_model.py`

Or, with Snakemake installed, steps 5-9 are just: `cd workflow && snakemake -j2 --cores 2`.

## One documented command that reproduces the headline result

```
python3 scripts/build_databases.py && python3 scripts/build_workloads.py && \
    cd scripts && python3 scaling_benchmark.py
```

This regenerates `results/tables/scaling_benchmark.json` and
`results/figures/scaling_curve.png` -- the measured speed-up of query
partitioning vs. database partitioning across 1/2/4/8 workers, which is
the project's headline finding (see report, Results).

## Data sources and the network limitation

This project's target data are the real NCBI nr/nt pre-formatted BLAST
databases, UniProt Swiss-Prot/TrEMBL, and a real SRA sequencing run. Every
accession and retrieval detail is listed in `data/raw/PROVENANCE.txt`
(generated by `scripts/fetch_data.sh`) and in the report's Data Sources
section.

The machine this project was developed and benchmarked on has network
egress restricted to a small allowlist that excludes direct FTP/HTTPS
access to `ftp.ncbi.nlm.nih.gov`, `ftp.uniprot.org` and `ebi.ac.uk`
(confirmed, not assumed -- see `scripts/fetch_data.sh` header comments).
`scripts/fetch_data.sh` therefore retrieves real, unmodified, real-
accession subsets of nr and UniProt TrEMBL/Swiss-Prot via the official
CI test fixtures of two actively-maintained bioinformatics tools
(DIAMOND, MMseqs2) that bundle exactly this kind of data for their own
reproducible benchmarking. Exact upstream git commit hashes are recorded
in `data/raw/PROVENANCE.txt`. On an unrestricted network (e.g. the
department cluster), the commented-out "PREFERRED" lines at the top of
`fetch_data.sh` retrieve the full, current databases directly from NCBI/
UniProt/SRA instead. This substitution, and what it means for how the
results should be read, is discussed in the report's Limitations section.
